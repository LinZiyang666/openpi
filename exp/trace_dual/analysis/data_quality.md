## 2. GPU 重放（`replay_pi05.py` / `replay_groot.py`）

用记录的服务端输入（原始图像、状态、prompt）和记录的 `noise_action_0` 重跑真实模型，与记录值逐项对比。每个模型抽 36 个样本，覆盖该模型全部 4 组，每集取首步、中间步、末步。

| | π0.5 | GR00T |
|---|---|---|
| `noise_action_0` 进入去噪循环后逐位一致 | 36/36 | 36/36 |
| 去噪循环每一步输入的误差（最大） | 1.8% | 0.2% |
| 最终动作 `clean_action` 的误差 | 平均 0.39%，最大 2.8% | 平均 0.07%，最大 0.3% |
| 同一样本换一组噪声重跑的差距 | 4.4%–156%，且每个样本都至少是其重放误差的 10.8 倍 | 112%–143% |
| vision / prompt embedding | ≤0.7% / 逐位一致 | 逐位一致 / 逐位一致 |
| robot_state | 不适用 | 35/36，差异原因见 §5 第 3 条 |

π0.5 的残余误差来自 server 端批量推理下的 bf16 数值差：误差沿去噪链逐步累积，重放时是 batch=1。GR00T 分阶段推理的第 1 阶段是确定性的，所以几乎可以逐位复现。结论：记录的噪声快照、embedding 和动作，确实就是模型当时算出来的值。

## 4. 核查过程中的两个口径更正（都是核查脚本的问题，不是数据的问题）

- `trace/search/twin_topk_per_field/*` 存的是**归一化之后**的逐字段分数，即 `0.5·(tanh((x−μ)/σ)+1)`，其中 l2 字段取 −距离；不是原始的 cosine 或 exp(−d)。按归一化口径比对后，误差 ≤ 1.9e-4。
- 读取性能：用 32 个进程并行扫描时，要用 `h5py.File(..., driver="core")`。默认读法会退化成每次约 90 KB 的随机读（本盘约 240 MB/s），`core` 读法下是每次约 525 KB（约 363 MB/s）。另外每个进程要设 `OMP_NUM_THREADS=1`，否则会严重超订。

## 5. 分析时要注意的点（数据本身没错，但容易踩坑）

1. **GR00T 动作块的填充维不是零。** 动作块形状是 (16, 32)，LIBERO 实际执行的只有前 7 维；第 7–31 维是没有训练信号的填充维，数值幅度约 0.45–0.65，看起来像噪声，cache 与推理在这些维上相差约 135%。π0.5 的填充维约为 0.001。所以凡是对整块动作算的距离（包括 trace 自带的 `error_proxies_json` 里的 `l2_full_hit_vs_full` 和 `max_*`），在 GR00T 上都会被填充维主导，GR00T 的 L2 约为 16–23，π0.5 约为 1.6–2.8。**比较动作时一律先切 `[:, :7]`。** 只看执行的 7 维，cache 与推理的相对差中位数为：spatial 0.31（GR00T）和 0.34（π0.5）；l10 为 0.74（GR00T）和 0.49（π0.5）。
2. **同一 init 跨组对比时，约 1–3% 的配对首帧有 1 个灰度级的渲染差。** GR00T 的视觉编码器对这种扰动相当敏感：单个像素差 1 级，个别 embedding 元素可能变化 39%，但整体 cos 仍 ≥ 0.9987。做跨组配对分析时，应该把它当作噪声底线，而不是信号。
3. **GR00T 的 `trace/raw_state` 以 float32 存储，而 server 收到的是 float64。** 用 raw_state 重新做归一化和 bf16 量化，约 0.1% 的步（1000 步中 1 步）会在某一维差 1 个 bf16 最小单位，因为那个值恰好落在舍入边界上，距离小于 float32 的存储精度。需要精确的模型输入时，应当直接用记录的 `robot_state`。
