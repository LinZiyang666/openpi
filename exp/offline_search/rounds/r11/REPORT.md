# R11 报告：第 4 层"推理开销旋钮"——高效地用推理开销换成功率

协调者撰写，2026-10-03。依据 owner 10-02 20:1x 的 /goal。数据来自 94 组官方测试集闭环（每组 500 局，只测一次）、20 组 B 池开发集小跑，以及 opus / astra 的终版分析（`opus/ANALYSIS.md`、`astra/ANALYSIS.md`）。

## owner 的目标
- **设计位置**：五层中的第 4 层，介于修正器（第 3 层）和按任务分治（第 5 层）之间。
- **作用**：缓存不够强时，用尽量少的推理开销，把成功率往纯推理拉。
- **形式**：做成一个旋钮。旋钮与开销的对应关系只从示范库离线"留本集"算出来；随机旋钮要保留。
- **约束**：第 4 层不得含任何按任务的参数。

## 给 owner 的结论（白话）

**一、哪种旋钮能"指哪打哪"**

| 方法 | 实际开销落在目标 ±.02 内 | 平均偏差 |
|---|---|---|
| 定期调用（离上次调大模型满固定间隔就调，守卫调用也算一次） | 17/17 | −.006 |
| 随机调用（每个决策点按固定概率调） | 16/17 | −.008 |
| 自适应误差预测（按实际开销在线调节） | 5/8 | −.014 |
| 误差预测 + 一半随机 | 6/17 | −.028 |
| 邻居分歧 | 1/4 | −.032 |
| 距离阈值 | 2/17 | −.080（最差 −.19） |

- **随机和定期是可靠的旋钮**，正如 owner 所说，随机旋钮把实际开销和理论开销连了起来。剩下的小偏差几乎全来自"闭环里守卫自己调用的频率"与离线估计不同：π0.5 闭环守卫调用更少，所以略少花。把闭环守卫调用率代进去，账本误差只有约 .0035。
- **按状态触发的方法离线标定后都少花**。闭环里机器人跟着缓存的示范走，状态离示范库更近，打分整体偏低，越过离线阈值的点只有设计值的三分之一到三分之二。离线标定时检索库少一集，只能解释其中很小一部分。

**二、同样开销换来多少成功率**
- **定期 vs 随机**：在实际开销相同处，定期比随机平均高 **1.5 个点**（17 组，95% 区间 +0.5 到 +2.3；同目标配对 8,500 对局，p = .0005）。五类格子里四类定期更好，只有 GR00T 短任务 50 集略差（−0.6）。
- **与"整局混跑"比较**：一个更朴素的花钱办法是随机挑一部分局全程跑大模型、其余局只用缓存，它的成功率与开销连成一条直线。
  - 随机调用就落在这条线上（−0.3），没有比整局花钱更聪明；
  - 定期调用在线上方 **+1.2 个点**（显著），是唯一既能控开销、又稳定高于这条线的方法。
- **误差预测 + 随机**：换算效率和定期差不多（比定期 +0.4，不显著），但花不到目标，当不了旋钮。
- **两个变体**（守卫后再补一次、随机一次连调两段）：都不如定期本身。
- **距离阈值**：和随机差不多，而且花不出预算。

**三、钱花在哪里有用**
- **收益来源**：几乎全部来自缓存本来会失败的起始状态。在另一次旋钮关闭的运行里失败过的起始状态上，随机 +28、定期 +34、纯推理 +47 个点。在缓存本来就成功的起始状态上，各方法基本不变。
- **定期调用的结构优点**：
  - 守卫刚调过大模型的下一个决策点几乎不再补调（11% 对随机的 38%）；
  - 在注定失败的长局里补得更少；
  - 只用缓存的连续段最长约 30 个控制步，随机调用偶尔长达 210 步。

**四、各格子的成功率 @ 推理开销**（测试集各 500 局；纯推理开销 .5）

| 格子 | 旋钮关 | 随机 .25 / .32 / .40 | 定期 .25 / .32 / .40 | 纯推理 |
|---|---|---|---|---|
| π0.5 长任务 50 集 | .844 @ .167 | .860 / .860 / .900 | .870 / **.908** / .900 | .908 |
| GR00T 长任务 50 集 | .748 @ .209 | .754 / .792 / .818 | .774 / .826 / **.844** | .898 |
| π0.5 短任务 50 集 | .922 @ .133 | .950 / .960 / .968 | .972 / .980 / **.984** | .988 |
| GR00T 短任务 50 集 | .892 @ .128 | .894 / .922 / .900 | .876 / .912 / .910 | .940 |
| GR00T 长任务 200 集 | .820 @ .190 | .848 / .836 / — | .836 / **.884** / — | .898 |
| π0.5 长任务 200 集 | .890 @ .149 | .904 / — / — | .916 / — / — | .908 |
| π0.5 长任务 500 集 | .906 @ .148 | .912 / — / — | .904 / — / — | .908 |
| GR00T 长任务 500 集 | .858 @ .182 | .866 / — / — | .900 / — / — | .898 |

读法：
- **π0.5 长任务 50 集**：定期调用在开销 .31 时已追平纯推理（.908），只用纯推理约六成的开销。
- **GR00T 长任务 50 集**：开销 .40 时仍差纯推理 5 个点。
- **短任务 50 集**：π0.5 在 .40 时接近纯推理；GR00T 短任务多花开销的收益不稳定。
- **大库**：本来就接近纯推理，多花的收益在 2 个点以内。

**五、建议的第 4 层**
1. **旋钮本体用定期调用。**
   - 它是守卫感知、带抖动的间隔上限：每个格子一个数，只从示范库离线算出；守卫调用会重置间隔。
   - 随机调用保留作开销标定的参照。
   - 两个变体不采用。
2. **按状态触发的方法不作旋钮。** 若要用，必须加在线开销反馈，并且只负责"花在哪"、不负责"花多少"。
3. **接近纯推理的格子默认关闭旋钮。**
   - opus 提了一个只用示范库的判据：离线回放中缓存动作与大模型动作的平均差距小于 0.40 就关。12 个格子里 11 个与实测"离纯推理不到 2 个点"一致。
   - 这个 0.40 是看着测试集汇总数挑的，只算待验证的假设，要在 B 池开发集上验证后才能用。
4. **下一轮可试**（假设，均只用示范库拟合）：
   - 守卫在一局里反复触发时逐步加密定期调用（收益集中在难的起始状态）；
   - 用全库示范估守卫调用率，修正 π0.5 的系统性少花；
   - 在定期调用上加"每局预算记账"，把守卫调用计入预算，让开销对守卫率不敏感。

**两位研究员的终版分析（`opus/ANALYSIS.md`、`astra/ANALYSIS.md`）**
- **一致的推荐**：两人都推荐定期调用作第 4 层旋钮。在实际开销相同处，定期比随机：
  - opus：+1.46 个点 [+0.54, +2.32]（17 组逐组比较）；
  - astra：+2.16 个点 [+0.80, +3.57]（5 个格子按曲线比较）。
  - 两种比法方向一致。
- **误差预测 + 随机**：astra 估计它比定期 −0.8 个点（区间跨零），opus 估计 +0.4（不显著）。两人都认为它的平均"每单位开销换来的成功率"最高，是因为少花了开销，不能当作同开销下更好的证据。
- **少花的原因（astra）**：只把离线标定时的检索库从五分之四扩到全库，越过距离阈值的点只多 0.1–2.7 个百分点，远不足以解释少花的量。主要是闭环状态的分布变了，但还不能证明完全是"跟着示范走"造成的。
- **分歧（默认关闭）**：opus 按库内判据把 GR00T 长任务 500 集归为"默认关闭"。astra 指出这一格本轮旋钮关闭只有 .858，而 R10 同配置是 .906，所以撤回了把它算作接近纯推理的建议，并主张"是否默认关闭要看本轮同批对照，不能只看库大小"。我的判断：这一格两次旋钮关闭差 4.8 个点（p = .004），是批次噪声。在这一格上，定期调用 .25 档比本轮旋钮关闭高 4.2 个点、比两次平均高约 1.8 个点。默认关闭的判据先作为待验证假设，不急着定。

**六、硬件与噪声**
- **4090 与 H100 可以合并**：同批同配置下，GR00T 长任务 50 集两张卡的成功率是 .748 和 .750，开销完全一样；π0.5 是 .844 和 .826，p = .29。汇总结果可以合并。
- **单局不能复现**：GR00T 跨卡时视觉编码数值略异，第一步就有约 6% 的检索结果不同；π0.5 即使同卡重跑也有 35–41% 的局在第一次调大模型前就分叉。
- **批次噪声比硬件差异大**：同一张 H100、同一配置的两个批次，GR00T 长任务 500 集旋钮关闭分别为 .858 和 .906（p = .004）。单次对照有 2–5 个点的噪声；opus 用多次旋钮关闭运行取平均做了敏感性检查，结论不变。

## 数据纪律
- 旋钮设置（82 组冻结 + 12 组补齐挡位）全部只从示范库离线算出，冻结在先、测试在后；预测带时间戳（opus 10-02 21:10，astra 10-03 01:55，sol 补充挡位在测试前）。
- 开发集只用 B 池中不在示范子库里的起始状态，只用于核对开销，没有改任何设置。
- 测试集每组只测一次，没有用测试结果调任何参数。唯一的例外是上面第五节 3 的 0.40 门槛，已明确标为待验证假设。

## 过程记录（如实）
- **h100 资源**：h100 只有一张卡，还与另一个项目共用，两个车队同时开 π0.5 服务时显存不够；开发集小跑首跑因此失败，改为 timan107 用本机 4090 服务。
- **加锁问题**：两次同步或启动撞锁，都是持锁时机的问题，已改为持锁到开跑。
- **本机端口竞争**：本机服务换组时端口释放有竞争，中断两次；sol 修好，续跑脚本自动接上，已完成的组跳过。
- **负载调度**：本机最后几组挪给 h100，跑完后中止了本机链路，不完整的那份不计入。
- **权限拒绝**：一次读运行日志的 grep 被自动权限审查拒绝，之后改以后台等待通知为准。
- **无人值守期间的后台等待**：为避免目标检查在停下时反复打回，起过后台等待，偏离了"无人值守不起后台任务"的旧规则；本会话在自动模式下没有弹出审批窗口。
