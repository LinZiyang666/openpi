# cache_prune：剪枝子库对纯 cache 成功率的影响（40 臂 × 500 集）

> 运行日 2026-09-12（CDT）。执行体 pi0.5（`pi05_libero`，PyTorch），全部臂为纯 cache：
> `always_search` + `always_hit`，Stage 1（SigLIP 视觉塔）提 key、CP1 检索、动作全部取自库，Stage 2/3 不跑。
> 评测 init 为两 suite 的官方 A-pool（10 任务 × 50 init，全部 500 个为两个源库都未见过的 common-unseen）。
> 数据：`data/direct_20260912/direct/<lane>/<suite>_<regime>/{journal,per_step}.jsonl`；
> 统计：`cache_prune_analysis.json`（`analyze_prune.py`，任务级两层配对 bootstrap 10,000 次，种子 20260911）；
> 图：`figures/cache_prune_curves.{png,pdf}`（底数据 `cache_prune_curves.json`）：上排成功率、中排与 P00 的配对差、下排成功集的平均控制步数。

## 1. 设计

两个源库 × 两个 suite，各按冻结网格剪成 10 个点（P00 = 不删；P01…P09 目标删除率 5/10/20/…/80%）：

| 源库 | 说明 | spatial 条目 | libero_10 条目 |
|---|---|---|---|
| rit50 | 50 条轨迹的小库（`cp1_spatial_pool_16.pkl`） | 1,018 | 2,640 |
| cs500_success | 500-init 成功轨迹库（cache_size S6） | 9,329 | 20,461 |

剪枝规则（`prune_library.select_retained`）：按冻结的检索分数矩阵，删掉那些在同任务内存在「分数 ≥ 阈值且进度更靠后（remaining 更小）、来自另一条轨迹」的邻居的条目；每条轨迹的终点永远保留。阈值由网格按目标删除率精确匹配。

每个 family（suite × regime）的 10 个臂在同一次 conductor 运行里评，同一批 500 个 init 配对；每集 FULL_HIT 见证率 40 臂全部 = 1.000。

## 2. 结果

列：删除率 = 实际删掉的条目比例；SR = 500 集成功率；ΔSR = 与 P00 的任务级配对差及 95% bootstrap 区间；
lost/new = 相对 P00 由成功变失败 / 由失败变成功的集数；ms/call = 在线每次推理调用的客户端耗时（含公网往返与服务端排队，只可 family 内横比）；steps = 平均控制步数。

## 3. 读数

1. **前 20–30% 的删除在四个 family 上都没有可分辨的代价**：P01–P03 的 ΔSR 95% 区间全部跨 0，
   点估计在 ±0.05 以内；libero_10/cs500 甚至到 P04（删 30%）仍是 −0.002。lost 与 new 数量相当，是配对噪声的样子。
2. **代价出现的位置随库大小后移**：ΔSR 区间首次整体落到 0 以下的点——
   spatial/rit50 P07（60%）、libero_10/rit50 P04（30%）、spatial/cs500 P06（50%）、libero_10/cs500 P08（70%）。
   大库（cs500）比小库更耐剪；libero_10 的小库最脆（P04 就掉 0.106）。
3. **删到 80% 的终点**：小库崩得厉害（spatial/rit50 从 0.664 到 0.120），大库仍保留大部分能力
   （spatial/cs500 0.808→0.606，libero_10/cs500 0.512→0.370）。
4. **成功集的长度**（图下排，只算各臂自己成功的集）：剪枝基本不改变一次成功要走多少步——
   spatial 两库都在 102–109 步之间，libero_10 在 240–258 步之间，与删除率没有单调关系；唯一的例外是 spatial 小库
   删到 70–80%（111、124 步，n 只剩 60）。表里"steps"列的单调上升是失败集撞步数上限拉高的全体平均。
   所以剪枝的代价几乎全部是"成功变失败"，不是"成功变慢"。
5. **在线检索耗时对库大小不敏感**：ms/call 在 family 内基本平（rit50 ≈150/190，cs500 ≈230–260/335–375），
   差异主要来自 suite 与 lane 链路，不是条目数；只用此列做 family 内相对比较。
   离线检索微基准（`benchmark_prune.py`）未跑。

## 4. 运行记录（摘要）

- 拓扑：lane A = h100（5 个 pi05 server 进程）↔ timan108（60 worker，3×A5000）；
  lane B = weilandserver（5 进程，4090）↔ timan107（60 worker，8×GTX1080）。lane A 跑 rit50 两 family，lane B 跑 cs500 两 family。
- 吞吐：spatial rit50 191 集/min（29 min），libero_10 rit50 109 集/min（55 min）；spatial cs500 140 集/min（42 min），
  libero_10 cs500 71 集/min（79 min）。20,000 集总计约 2 小时（14:17–16:19 CDT）。
- 一次故障：lane A 换 family 重启 server 后 worker 复用死 websocket，`select_bundle` 连续失败把重试额度耗尽；
  修复 `episode_runner.py`（异常后丢弃连接）并以 journal 续跑，见 `logs/cache_prune_run_progress.md`。
- 基础设施错误 0；40 臂 FULL_HIT 见证率全部 1.000；每臂 500 集齐全。
